## PLAN

Verify format, one time display, hashing, the two active key limit, recent authentication, revocation and cache purge through HTTP, and inspect the stored row.

## CALL

```powershell
cd backend
```

## PAUSE

```text
✔ key creation needs a recent password confirmation and returns the secret once
✔ revocation takes effect immediately and the audit chain stays valid
```

Assertions that ran:

- A key for an unverified site returns `403 site_not_verified`.
- A key without recent authentication returns `403 recent_auth_required`.
- An analyst receives `403`.
- The key matches `^sfk_[a-z2-7]{12}_[A-Za-z0-9_-]{43}$`.
- `Cache-Control` is `no-store`.
- The last four characters match the stored `last4`.
- A second key is allowed; a third returns `409 key_limit_reached`.
- Key metadata contains no `apiKey`, `secret_hash` or `secretHash`.
- After revocation the key returns `401 invalid_api_key` on the next ingestion.
- The audit chain verifies, and the audit response contains neither the key nor a challenge token.

## INTEGRATE

All pass criteria met. The secret exists in the response and in the creation stack only. Only a SHA-256 hash is stored.

## ACT

The smoke script initially created a key without a step-up and received `recent_auth_required`, which confirmed the control before the integration test encoded it.

## RECORD

W2.1 is VERIFIED. Rotation is create the second key, deploy it, revoke the first. There is no automatic rotation job, which is documented.

## Security second pass

1. Revoked key reuse: rejected immediately, cache purged. Tested.
2. Unknown key id: constant comparison path. Implemented; no timing measurement.
3. Cross site use: site is resolved from the key, not from the body. Tested by tenant isolation.
4. Key in logs or audit: audit stores key id and last four only. Asserted.
5. Concurrent creation beyond the limit: creation runs under `BEGIN IMMEDIATE` and re-counts. Reviewed, not load tested.
