# Security

This document describes what the application actually enforces, how it was verified, and what remains a known gap. It is not a certification.

## Authentication

- Passwords are hashed with scrypt and a per user random salt; the format is `scrypt$salt$digest` and verification uses `timingSafeEqual`.
- Optional TOTP multi-factor authentication. Enrolment requires the current password; login with MFA returns a five minute challenge instead of a session, and no cookie is issued until a valid six digit code is presented. Eight single use recovery codes are stored as SHA-256 hashes. Recovery codes are removed when used.
- Session tokens are 32 random bytes (base64url). Only the SHA-256 digest is stored, so a database read does not yield usable cookies.
- At most ten sessions are retained per user; the oldest is dropped. Changing a password deletes every session and issues a fresh one. "Sign out other sessions" is available in Settings.
- Cookie flags: `HttpOnly`, `SameSite=Lax`, `Path=/`, seven day expiry. `Secure` is added when `NODE_ENV=production`.
- Login failures return the same message and status for an unknown email and a wrong password, so the endpoint does not disclose account existence.
- Disabling a member deletes their sessions immediately.
- Login is rate limited to 12 attempts per 15 minutes per IP. Registration is limited to 6 per hour.

## Authorization

- Three roles: `viewer` (read), `analyst` (operational writes), `admin` (users, settings, integrations, rule enablement, deletion).
- Every router applies `requireAuth`; writes apply `requireRole` on the server. Hiding a button in the client is never the control.
- Self service guardrails: an admin cannot remove their own admin role, and the last active admin cannot be demoted or disabled.

## Tenant isolation

- `org_id` is written from `req.user.orgId` on create and added to the `WHERE` clause on every read, update and delete.
- Client supplied `orgId` / `organizationId` fields are ignored by the schemas.
- Cross-tenant fetches return `404`, not `403`, so the existence of another organization's records is not disclosed.
- Verified by tests: a second workspace cannot read, patch, delete or start another workspace's asset, incident or simulation, and the demo workspace cannot see the second workspace's records.

## Request integrity

- `SameSite=Lax` plus an `Origin`/`Host` comparison on every non-GET request. Cross-origin writes are rejected with `origin_rejected`.
- JSON bodies are parsed with an 8 MB limit; URL encoded bodies with a 1 MB limit.
- All input passes through Zod schemas with explicit types, lengths and enums. Unknown fields are stripped.
- SQL uses prepared statements with positional parameters. No string interpolation of user input reaches SQL.

## SSRF protection (URL scanner)

- Only `http` and `https`.
- Rejects URLs with embedded credentials, `localhost`, `*.local`, `*.internal`.
- Resolves the hostname and rejects any address in loopback, private, link local, multicast, reserved, documentation or IPv6 unique local ranges, including IPv4 mapped IPv6.
- Re-resolves and re-validates every redirect hop; redirects are capped at three.
- The address is pinned at connection time through a custom DNS lookup, so a second DNS answer cannot rebind the socket to a private range between validation and connect.
- Six second timeout per request, 256 kB response cap, no script execution, no form submission, no rendering of remote HTML.
- Access to a private address is refused before a request is made; verified by tests against `127.0.0.1`, `10.20.0.5`, `192.168.1.1`, `172.16.4.4`, `169.254.169.254`, `[::1]`, `0.0.0.0` and `100.64.1.1`.

## File uploads and evidence

- JSON base64 upload with a 5 MB decoded limit and a MIME allowlist.
- Filenames are reduced to a basename and stripped of path separators; storage names are generated by the server.
- The resolved storage path must remain inside the evidence directory (path traversal guard), checked again on download and verify.
- SHA-256 is computed on intake, recorded in the custody trail, and recomputed on demand. A tampered file reports `match: false`; this is covered by a test that overwrites the stored file.
- Downloads set `X-Evidence-SHA256` and `Content-Disposition` with a sanitised filename.

## Secrets and data exposure

- Provider keys are read from the process environment only. The settings API rejects keys matching `key`, `token`, `secret` or `password`.
- The client never receives a database path, service key or session token value.
- The production build contains no secrets; the bundle is static JavaScript with the API origin only.
- Responses omit stack traces. Errors are logged server side with request method and path.

## Headers

`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` disabling camera, microphone and geolocation, `Cross-Origin-Opener-Policy: same-origin`, and a Content-Security-Policy on served HTML (`default-src 'self'`, no inline scripts, `frame-ancestors 'none'`). HSTS is intentionally left to the reverse proxy, because it must only be enabled once HTTPS works on every hostname.

## Audit trail

Security sensitive actions append to `audit_logs`: registration, login, logout, profile changes, asset and indicator changes, incident creation and status changes, rule changes, simulation creation/start/cancel/delete, workflow execution and approval, evidence access, integration changes and report generation. The trail is readable by admins in the UI.

## Demo mode and first admin

Demo mode seeds a synthetic workspace with known accounts (`admin@secureflow.dev` and two others). It is **on by default outside production and off when `NODE_ENV=production`**. In production, an empty database is never seeded with a public password: the server requires `SF_BOOTSTRAP_EMAIL` and `SF_BOOTSTRAP_PASSWORD` (12 or more characters) to create the first admin, and exits with instructions if they are missing. `SF_DEMO_MODE=true` can force demo mode on a throwaway deployment.

The demo passwords are no longer compiled into the client bundle. The login page fetches `/api/auth/demo-accounts`, which returns an empty list unless demo mode is on. Verified: a production bundle built from this source contains no demo password string.

Run a real deployment with demo mode off, a bootstrap admin you control, and demo data removed.

## Known gaps

| Gap | Impact | Mitigation |
| --- | --- | --- |
| No password reset flow or email | Users cannot self-recover | Admin creates a new password via People and Settings |
| TOTP only, no WebAuthn or SSO | Phishing proxies can relay codes; no hardware key support | Add WebAuthn and SAML/OIDC in a future release |
| No CSRF token, only origin check plus SameSite | Older browsers without SameSite support are weaker | Keep the app same-origin; add a per-session token if embedding changes |
| In-process rate limits | Limits reset on restart and are per instance | Move to a shared store when scaling horizontally |
| Session is not bound to a device fingerprint | A stolen cookie works until expiry | Rotate on privilege change and keep the session list short |
| No antivirus scanning of uploaded evidence | A stored file could be malicious | Keep evidence out of any web root; scan before opening |
| SQLite has no row level security | Isolation relies on application code | Covered by tests; move to PostgreSQL RLS for defence in depth |
| Integration collectors are not implemented | No automatic telemetry from Wazuh, Sysmon, Suricata, Zeek, ClamAV or YARA | Use the ingestion API; adapters are a documented backlog item |
| No deployment here | TLS, HSTS and host hardening are untested in a live environment | Follow DEPLOYMENT.md on a host you control |

## Reporting a vulnerability

Do not open a public issue for a live vulnerability. Contact the operator of the deployment. If you are working from this repository, open a private security advisory with reproduction steps, affected endpoint and impact. Never include real credentials or customer data.
